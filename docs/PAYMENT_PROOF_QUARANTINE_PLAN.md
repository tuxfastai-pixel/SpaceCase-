# Payment proof — private receiving foundation

22 November 2026. ACT-PAY-04-QUARANTINE. Source-only implementation slice; no browser upload, public route, scanner, Finance receipt link or hosted activation.

## Goal and acceptance

Prepare the receiving boundary for the parent flow **I have paid → Choose proof → Check amount/date/reference → Submit → Track review**. Complete this foundation with strict input/file bounds, current purpose-specific authority, private quarantine, deterministic retries, current-scope status lookup, explicit retention configuration and restricted-runtime lifecycle tests. A file submission cannot change invoices, receipts, allocations, accepted activity plans or authority.

This slice deliberately has no file-release capability. A signature match means only a supported candidate for quarantine; it does not mean the document is valid, malware-free, genuine, or paid. Do not expose the receiving service directly to a parent while the following release dependencies are unfinished.

## Boundaries and failure cases

- PEOS `family-billing-v1` already names `family.finance.proof.submit`. Existing billing-read or activity-plan grants do not authorize proof submission. Resolve school/learner/person exclusively from a current decision; recheck exact scope and permission before commit or status return, including retries. No new grants or PEOS changes in this slice.
- The strict claim has positive bounded integer cents, a real payment date no later than today's Africa/Johannesburg date, a bounded reference and payment method. No parent-supplied verification, school/account/learner selector, file URL or receipt ID.
- Maximum file size is 2 MiB; only JPEG, PNG and PDF candidates with matching basic signatures are accepted into quarantine. Copy the input bytes before hashing/storage. Do not execute, parse for display, render, extract or serve a file here. Never use onboarding photo URLs or public Blob links for payment evidence.
- Private PostgreSQL binary quarantine is separated from immutable case metadata and request aliases. No filename or document contents in audit metadata. Ordinary web runtime has INSERT-only access to quarantined bytes, not SELECT/UPDATE/DELETE. It may SELECT/INSERT case metadata/request rows, not overwrite/delete history. No SECURITY DEFINER or schema creation privilege.
- Account locking serializes request identity, duplicate-file checks and quotas. The digest binds grant, claims, MIME and file hash. Same-key/same-payload replay returns the same case after current authorization; changed payload fails. Same owner/learner/school file with identical claims and a new request key receives a durable alias to the existing case; changed claims fail. Cross-parent/cross-child/cross-school records are not disclosed. Cross-owner matching is reserved for a later authorized Finance duplicate review and must not disclose another family's case to a parent.
- Explicit trusted server configuration is required: version, 1–72 quarantine hours, bounded rolling-24-hour person request limit, bounded account byte budget. No default school financial retention policy is inferred. Duplicate request aliases count toward the request quota; exact same-key recovery is allowed after quota. Metadata quota calculations do not need raw-file read permission.
- Status exposes owner-scoped claimed amount/date/reference/method, timestamps and QUARANTINED/EXPIRED only. No hashes, bytes, canonical IDs or verification claim. Expiry is enforced in the read result even before physical cleanup. An expired proof is not resurrected or represented as newly uploaded when retried.
- A separately provisioned `spacecase_proof_cleanup` role can delete expired binary rows in batches of at most 100 and append an opaque purge record atomically. Migration grants privileges only if that role already exists, and does not create a login, credentials, role membership or scheduler. Normal web runtime cannot run cleanup. Metadata/audit history remains. Active quarantined files are not deleted. A future production cleanup schedule, monitoring and backup expiry handling are release requirements; a successful test is not an operational retention guarantee.

## ACT-PAY-04-SCAN — internal scanner and private file boundary

22 November 2026. Continues the same unmerged proof work. Scope: real ClamAV Unix-socket adapter, trusted hash-bound preparation, scanner-role persistence, authorized cleared-file reads and byte-only expiry cleanup. No HTTP route, UI, scheduler, provider account, hosted migration or upload activation.

Protocol basis: [official ClamD protocol](https://docs.clamav.net/manual/Usage/ClamdProtocol.html). The adapter uses framed `VERSIONCOMMANDS`/`INSTREAM`, bounded replies/streams/timeouts and no public TCP connection. The socket and containing directory must not be world-writable; configured socket permissions and worker deployment remain operator requirements. ClamAV and worker should use UTC/English-compatible version dates; unparseable/stale/future definitions, unsupported streaming, ambiguous/multiple/unterminated replies and daemon errors fail closed. No command strings, file paths, raw replies, detected signature names or bank content enter product audit logs. Actual daemon/signature installation, updates and synthetic safe/malware validation remain release gates; socket simulator tests are protocol tests, not a real engine scan.

Original bytes are scanned before processing; raster JPEG/PNG candidates must decode within a 16-million-pixel single-frame limit and are rotated/flattened/re-encoded as JPEG without metadata. Derived bytes are scanned again. PDFs remain unchanged after scanning and are attachment-only, not rendered by the app; scanner clearance is not document authenticity or payment verification. Each verdict must match the bytes and have a recent checked time. A prior blocked attempt cannot be silently overridden by a later worker retry. At most three recorded attempts per case per rolling day; the scheduler must also back off failures. No scanner is provided by a browser request.

New migration `20261122130000_payment_proof_scan_boundary.sql` separates immutable scan attempts/clearance metadata from deletable `payment_proof_cleared_files` bytes. A separately provisioned non-login scanner role can read quarantine and insert scan metadata/cleared files, with no invoice/payment writes, updates or deletion. Normal web runtime can read cleared bytes/metadata but cannot declare a clean file or read quarantine. Current original proof-submit authority must be checked before worker processing and at commit through a trusted canonical adapter; that background PEOS service integration is not implemented here. Account/case/advisory checks prevent duplicate clearance and missing/expired sources. Concurrent workers retain a single clearance.

Clean-file retention has a separate mandatory server policy version and bounded 1–3650 day setting. These bounds do not select a school retention policy or claim legal compliance. No default is configured. Read denial follows expiry immediately; a dedicated cleanup role deletes only expired file bytes in bounded batches, retaining hashes, scan/definition provenance, claim metadata and purge history. A processed/purged file cannot be reissued by rerunning the worker. Backup expiry, metadata retention/deletion, incident response and monitored cleanup schedules remain operational dependencies before collecting real documents.

Private family reads require current billing-read permission and the exact submitting person, learner and school; another caregiver does not inherit the submitter's document. Staff reads require current school/account Finance transactions-read authority. Both recheck authority and append opaque read audits. Files must still match their stored hash and source association. Response headers are private/no-store, attachment with opaque generated filename, exact content type, nosniff and CSP sandbox. No public Blob URL, long-lived download token, inline PDF, OCR or bank-verification claim. Status is READY_FOR_REVIEW / FILE_BLOCKED / QUARANTINED / EXPIRED, never paid.

Acceptance: protocol framing/failure tests, raster normalization/re-scan/hash mismatch and download-header tests, real PostgreSQL worker/web/cleanup role tests, current/revoked/cross-scope reads, blocked/retry/concurrent/expiry/history/unchanged-ledger lifecycle. Local image/header tests and type/lint pass; local socket tests hit a native runtime assertion before completion, so protocol validation is delegated to normal Node CI. Full CI and final evidence pending. No real documents are scanned or transmitted, and no operational daemon or background service is installed.
