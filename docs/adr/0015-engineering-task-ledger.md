# ADR 0015 — PSG engineering task storage

Decision: persist reviewed engineering tasks in a dedicated PSG-owned PostgreSQL database. Source lives in the PSG service workspace; the SpaceCase database and migration runner do not own or receive these tables. Existing PEOS identity remains authoritative. A trusted adapter must supply fresh founder authority and the current source revision/open state; these values must never come from a public request body.

Failure analysis: retries or concurrent clicks could create duplicate jobs; cancellation racing a worker could revive old work; a copied handoff could change policy; audit logs could disclose source narratives; sharing the school database credentials with an agent could expose learner data. There is no runner in this stage, so the database permits only BLOCKED and CANCELLED. A cancelled task never resumes through resubmission. Starting execution requires a separately reviewed migration and authenticated sandbox adapter.

The internal ledger service validates the canonical preflight before storage. Actor/request UUID retries serialize with an advisory transaction lock and an immutable payload hash. A unique project/reference/revision/digest/base-commit tuple converges distinct submissions of identical reviewed work. A changed payload using an old request UUID fails. Tasks preserve the reviewed brief and commit; events contain only task, actor, transition and revision. Saving an existing task returns its current state without creating another creation event. Cancellation takes a row lock and requires the expected task revision, with its event committed atomically.

The runtime role may insert/read tasks and append request/event records; only task state, revision and cancellation time can be updated. It cannot change a stored brief or delete/update audit events. Schema creation and migration history are unavailable to this role. The migration runner checks for known product schemas before writing and refuses a missing or privileged runtime role. Use a dedicated database and credentials; this guard is additional protection, not proof of deployment ownership.

This change exposes no HTTP route and provisions no production database. It does not alter the ephemeral Stage 1 UI or copy data to PSG. Pilot activation requires an authenticated product adapter, explicit founder save consent, deployment-scoped database credentials, a retention/purge policy for reviewed briefs and a separately validated schema deployment. No credentials, inference spend, model access, repository access or automatic release authority are introduced.

Acceptance: real PostgreSQL tests exercise runtime grants, concurrent duplicate requests, payload conflicts, persistence across connections, cancellation races and append-only events. CI creates a separate disposable engineering database; no production school records are used.
