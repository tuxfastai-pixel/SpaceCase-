# ADR 0016 — Purpose-scoped authenticated engineering saves

Decision: connect the existing founder API to a PSG-owned ledger endpoint using a short-lived Ed25519-signed save attestation. SpaceCase holds the private signing key; PSG receives only the public verification key. The payload fixes issuer, audience, contract version and SAVE_BLOCKED_TASK purpose and binds actor, request UUID, canonical handoff/digest and full base commit. No login bearer, cookie, raw source narrative, school identifier or reporter identity is forwarded. Reviewed briefs remain a manual privacy responsibility, not automatic redaction.

Failure analysis: forwarding a founder session would give the recipient unnecessary account authority. A shared symmetric secret would let the recipient mint issuer approvals. An unsigned founder boolean could bypass authorization. Redirects could disclose reviewed content to another host. Replays could duplicate tasks, or an altered response could falsely acknowledge unrelated work. A save authorization must never become permission to execute code or deploy.

Every founder SAVE_ENGINEERING_TASK request passes existing same-origin, session and freshly resolved PEOS founder checks. Input additionally requires privacyReviewed=true and consentToStore=true. The product rereads and locks the open ticket, validates its expected revision, creates the canonical handoff and audits its digest. It commits that product transaction before making a network call. The signed request expires after 30 seconds (up to 5 seconds of future clock skew is tolerated), has a 64KiB payload cap and conveys only a snapshot of founder/source validity at issuance. A ticket or role may change while this short request is in flight. Storing a blocked snapshot is acceptable; future execution must independently recheck current authority and source revision. This attestation is never an execution permit.

PSG POST /v1/engineering/tasks accepts only a bounded signed envelope. It verifies the configured public key, purpose, audience, age and canonical handoff before opening storage. Its ledger enforces actor/request idempotency and immutable reviewed-work identity. Replaying an accepted request returns the existing current task, including cancellation; it cannot restart work. The product validates the bounded acknowledgement against source reference/revision, digest and exact base commit before reporting success. Transport failure leaves an unknown outcome: callers must retry the same request UUID and payload, not invent a new request to assume failure.

Both sides default disabled and require explicit production deployment scope. Previews cannot send to or store in the production ledger even if credentials were accidentally supplied. HTTPS origin is server-configured, not accepted from input; redirects are rejected. Verification failures and disabled/missing configuration fail before database access. Signed payloads, private keys and session credentials must never be logged. Public-key rotation invalidates in-flight requests; operators can retry with the same reviewed work and request UUID after rotation.

No production key or storage configuration is provisioned here. The existing founder UI remains an ephemeral preparation/copy flow. Activation still requires dedicated restricted ledger storage, reviewed-brief retention/purge configuration, scoped production key installation and an explicit consent/save UI. No runner, worker claim, inference, repository access, cancellation API or release authorization is introduced.

Validation uses generated ephemeral keys and synthetic product/ledger databases. It covers forged/wrong-key/purpose/audience/expired/oversized requests, preview/disabled configuration, unexpected authority input, stale/closed source denial, retry conflicts, cross-service privacy, real persistence and acknowledgement binding. PSG database tests run serially because migration ACL tests temporarily change permissions in the disposable test database.
