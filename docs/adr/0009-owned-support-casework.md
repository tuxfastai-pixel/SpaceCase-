# ADR 0009: owned support casework
The read-only observer role remains separate from the new school-scoped SPACECASE_SUPPORT_AGENT role. Only the founder can grant either, for at most 30 days, through PEOS. Existing observer grants do not become agent grants. Canonical context supplies separate agentSchools and observerSchools; missing agentSchools fails closed.
Agents see only metadata until claiming an unassigned case. Narrative reads, public replies, release and escalation require current school agent authority plus ownership. A founder may assign only a currently eligible canonical agent for that school, or clear an owner. Revocation/expiry prevents subsequent case access; abandoned cases require founder reassignment. No automatic takeover or broad learner access.
Ticket row locks arbitrate ownership and the existing ticket revision protects concurrent reporter/staff/founder edits. Actor/request UUID and payload hash provide retry idempotency; mismatched request reuse returns a conflict. Shared lock ordering is actor request then ticket then work row. Only current ticket owners can change their casework; agents cannot close cases, set priority or alter founder approval decisions. Replies preserve founder-planned status.
Migration 0010 adds support.ticket_work, append-only support.work_events and support.work_requests. Ownership history records actor and from/to owner identifiers. Internal escalation reasons/history never enter reporter timelines, observer metadata, metrics or public logs. Runtime can update current work but cannot update/delete events or request receipts. No record deletion is part of release/rollback.
Agent replies use existing TECHNICAL_UPDATE reporter events; they are in-app technical support responses, not teacher evaluations. Claims do not manufacture public replies. Explicit escalations enter the founder inbox; founder acknowledgement does not imply a fix or deployment. Escalation timestamps are stored separately from later assignment edits.
UI discloses assigned staff visibility before reports are submitted. No real staff grants, emails, external notifications, AI invocations, repairs, billing or suspension changes occur in this implementation.
Validation covers observer denial, school/ownership privacy, concurrent claims, retry safety, revoked authority, private escalation, reassignment and status governance. Full CI and isolated Neon runtime checks are required. Production completion of the prepared Neon migration requires user confirmation under the tool instructions; deploy the PEOS contract before dependent SpaceCase code. Signed-in browser verification remains outstanding without an authenticated session.
